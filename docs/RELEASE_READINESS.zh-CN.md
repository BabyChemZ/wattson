# Wattson：发布判断与 AI / agent 方向

调研日期：2026-09-07。以本地 `671a2bd` 为修复起点。本文区分已经实现、建议验证和未来设计；排期是工程估计，不是已完成结果。

## 结论

Wattson 可以作为独立开源项目发布，并且可以先发布无 Developer ID 签名、无公证的预览 ZIP。签名不是当前阶段的前置条件。当前合理定位是 **面向本地 AI 和 coding agent 工作负载的资源监控与守护工具**。

“更多系统指标”和“降低后台进程 CPU”已有成熟产品覆盖。最值得进一步验证的方向，是 **以任务为单位管理资源：归属、准入、并发、结束清理和效果记录**。无需替换 macOS 内核调度器，也不需要再找一个完全无关的 idea。

## 修复后具备什么

- 只观察模式覆盖异常处置与推理让路；模拟动作不产生真实恢复义务。
- 网络采样缺失与真实零吞吐分开；缺失值不作为网络停滞证据。
- 自动降优先级使用 PID、启动时间、UID、可执行文件路径识别目标，并核对当前进程。
- 每个优先级请求有归属。异常处置和推理让路不会互相撤销；退出、关闭自动处置、采样丢失时会撤销自己的请求。失败的恢复保留记录并重试，重启后读取恢复记录。
- 不覆盖已经存在的后台策略；读不到原始策略时不自动修改。
- 自动 SIGTERM 路径已移除。持续异常最终交给用户检查，界面手动结束仍需确认。
- SIGTERM 退出可保存基线；跨天样本容量、自身名称保护和已知 CPU 状态下的异常持续时间已修复。
- `scripts/test.sh` 编译实际生产源代码执行回归，不依赖完整 Xcode / XCTest；`scripts/smoke-test.py` 使用独立数据目录和只观察模式。

这些验证证明覆盖到的行为成立，不能替代跨机器和长时间测试。持续时间判定至少要求三次历史突发，超过历史最长的 1.5 倍且至少多五分钟；这是当前启发式规则，不是已校准的概率模型。

## 与现有产品有什么区别

| 产品或方向 | 已有能力 / 主要问题 | 对 Wattson 的含义 |
|---|---|---|
| Stats | 菜单栏 CPU、GPU、内存、磁盘、网络、电池、传感器、蓝牙、时钟；成熟的通用系统仪表盘 | 通用图表不是我们足够强的差异；硬件覆盖、兼容性和低开销需要长期积累 |
| iStat Menus | 通用系统监控与菜单栏体验 | 不能只靠界面或“指标更多”建立长期价值 |
| App Tamer | 自动放慢或暂停后台应用，提供 CPU 使用控制和 Apple Silicon 后台负载管理 | “Mac 上控制别人的 CPU”已经有产品，不应作为全新卖点 |
| 当前 Wattson | 程序历史基线、推理环境记录、离开报告、遗留进程启发式、受限的自动优先级调整 | 已足以形成一个可试用的独立原型；任务归属与因果判断仍不完整 |
| 建议发展的 Wattson | 管理 agent 提交的任务，按内存和并发预算排队，记录任务成本，按所有权清理 | 可以围绕一条明确用户路径继续演进，但这些功能尚未实现 |

上表对竞品的描述来自其官方功能页，不表示已穷尽每个插件或历史版本，也不证明 Wattson 是市场上唯一采用某种方法的工具。[Stats 官方仓库](https://github.com/exelban/stats)、[iStat Menus 官方页](https://bjango.com/mac/istatmenus/)、[App Tamer 官方页](https://www.stclairsoft.com/AppTamer/)。

## macOS 允许哪一层“调度”

| 层次 | 能否做 | 实际边界 |
|---|---|---|
| 监控资源 | 可以 | 有些读取需要权限，有些 SMC / IOReport 接口缺少稳定的公开契约，必须按硬件和系统版本验证 |
| 请求 CPU / I/O 优先级 | 可以 | QoS、后台策略和 nice 表达重要程度；权限限制和最终调度仍由系统决定 |
| 为自有任务限制并发、排队、延后启动 | 可以，而且适合作为核心 | 例如机器只接纳一个大型本地模型任务，同时允许两个轻量测试；剩余任务暂不启动 |
| 控制自有或明确授权的进程生命周期 | 可以 | 可以启动、等待、发送信号；暂停不会释放内存，可能持有锁，不能对任意工作负载承诺透明暂停恢复 |
| 协作管理模型内存 | 可以，通过运行时接口 | 对支持的模型服务器主动卸载闲置模型、改变请求并发；不能通用地强制别人的 malloc 或 GPU allocation 释放 |
| 固定 P / E 核、替换系统调度器 | 不作为普通应用的产品承诺 | Apple 的公开推荐路径是 GCD / QoS，系统还会根据温度等因素改变核心可用性 |
| 任意 macOS 原生进程的 Linux cgroup 式 CPU / RAM / GPU 硬配额 | 不应承诺 | 自有 worker 的并发和内存预算是应用策略，不等于内核强制隔离；VM 内的限制只作用于 VM 工作负载 |

Apple 说明 QoS 会影响调度、CPU / I/O 吞吐和计时行为，Apple Silicon 上系统决定适合的核心类型。`taskpolicy -b` 对应后台策略，`-B` 退出该后台状态；本机手册也说明后台策略会影响 I/O 和部分网络活动。因此产品文案已改为“请求后台优先级”，不能保证“把进程锁在能效核”。[Apple QoS 指南](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html)、[Apple Silicon 优化文档](https://developer.apple.com/documentation/apple-silicon/tuning-your-code-s-performance-for-apple-silicon/)、[Apple CPU job scheduling 说明](https://developer.apple.com/videos/play/tech-talks/110147/)。

Ollama 已提供模型驻留时间 / 卸载、模型并发数和请求队列设置；这证明应用层可以在“启动之前、请求进入之前”管理负载。Wattson 的潜在价值在于协调多个运行时、测试和 agent 任务，不是重复实现一个 Ollama 已有的队列。[Ollama 官方 FAQ](https://docs.ollama.com/faq)。

## 建议只推进一条核心工作流

设想一个人同时开着两个 coding agent，又在本地跑模型。目前程序名只显示 `Python` / `node`，无法可靠判断属于哪个任务；祖先进程退出后，树结构还会丢失。

下一阶段优先新增一个显式托管入口，以下只是接口草案，**当前 CLI 尚不支持**：

```text
wattson run --project my-repo --kind test --memory-estimate 4G -- <command> <args>
```

它应完成一件闭环的事：

1. 任务启动时登记项目、agent 会话、工作目录、是否交互、是否允许长期驻留、预计内存；由入口建立可追踪的进程组和身份记录。
2. 准入器结合当前内存压力和已经接纳的任务预算，决定立即运行还是排队；允许用户覆盖策略。预算不宣称是硬性内存上限。
3. UI 显示“哪个任务在用资源、为什么另一个在等”，而不是要求人从几十个 node 进程里猜。
4. 会话结束后，仅清理明确归属且不被标为长期服务的 worker；未知进程只提示。不要把父进程退出当作用户同意结束所有后代。
5. 输出结果：退出码、墙钟时间、峰值进程内存、整机压力区间、采样覆盖率、清理结果。tokens/s 需要对应运行时提供，不从 CPU/GPU 占用反推。

之后再把这个入口接到 agent hooks 或 MCP。接口价值来自准确的任务所有权和可执行策略；加一个聊天框不会自动解决资源管理问题。

## 什么时候发布

| 阶段 | 建议时机 | 放行依据 |
|---|---|---|
| 开源预览 / 朋友试用 | 本轮包通过检查后即可 | arm64 预览 ZIP、安装说明、默认只观察、已知限制、校验值；不等待开发者签名 |
| 公开 beta | 建议收集约 1–2 周反馈后评估 | 至少 3 台不同 M 系列机器、2 个声明支持的系统版本；连续运行、睡眠唤醒、退出恢复、升级与登录启动均有记录 |
| 面向长期使用的稳定版 | 由验证结果决定，不能现在承诺日期 | 长时间无错误处置 / 无遗留优先级，兼容性范围明确，数据迁移和卸载可用，有回滚路径和持续回归 |
| agent 任务管理 MVP | 范围固定后估计 2–4 周 | 一条从提交、排队、运行到清理的真实任务链跑通；至少一种 agent 工作流和一个本地模型运行时 |

这些时间窗是建议排期。签名不在当前放行门槛里；未公证主要增加首次安装阻力，不会使应用功能天然不可用。源码公开与 GitHub Release 发布是两件事，本次查看 Releases 页未发现已发布附件。[项目 Releases](https://github.com/BabyChemZ/wattson/releases)。

当前仍需要验证或改进：

- 当前样本来自一台机器，最低 macOS 13 编译目标不等于已经测试兼容。
- 程序名基线会混合不同 Python / node 任务，不能代替任务身份；top-N 采样仍可能遗漏短命或安静进程。
- 推理识别和阶段是启发式；整机 GPU / swap / 热压力不能直接归因给一个模型。多个运行时同时存在时，当前单会话模型还有边界。
- Energy Impact 的积分是相对指标；没有实测证据就不承诺减少多少电量、温度或模型延迟。
- 登录启动、升级、重复 GUI 实例、长时间运行和不同硬件还需要专门验证。
- 旧截图可能保留早期重启文案；正式宣传素材需要按最终行为刷新。

## 怎样验证这个方向值得继续

做三个可重现案例：多个 agent 同时启动构建 / 测试导致内存压力；本地模型和构建争用资源；任务退出后遗留 dev server。先用自己提交的任务建立可确认的归属，不用盲猜代理进程。

同一台机器、同一批任务和数据，比较系统默认运行、手工限制并发、Wattson 任务准入。记录完整完成时间、交互响应、峰值内存、压力持续时间、失败 / 重试次数和清理准确率。重复多轮并报告变化范围；云端模型响应变慢要单独记录，不能归因本机调度。

若只比“无限制地同时开所有任务”更好，而不比简单固定并发更好，那么动态调度暂时没有证明优势。即便如此，任务归属、清理和报告仍可能有独立价值，应通过测试者使用反馈判断。

## 给别人使用

把预览 ZIP 和校验值发给测试者，附带 [安装说明](INSTALL_PREVIEW.zh-CN.md)。测试者不需要开发环境。首次打开按 Apple 的“隐私与安全 → 仍要打开”流程操作；企业管理策略可能限制此例外。[Apple 官方说明](https://support.apple.com/zh-cn/102445)。

广泛分发以后再考虑 Developer ID / 公证和自动更新，不影响现在试用。Mac App Store 则需要单独评估：审核要求公开 API，Mac 应用还要求 App Sandbox；当前私有传感器读取、跨进程管理和管理员功能不能直接假定可原样上架。因此当前优先使用 GitHub ZIP 分发。[Apple 审核规则](https://developer.apple.com/app-store/review/guidelines/)、[App Sandbox 文档](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox)。
